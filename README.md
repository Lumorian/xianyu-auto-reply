# 🐟 闲鱼自动发货工具

买家拍下并付款后，自动把卡密 / 发货文案发到私信里，并按需点掉「无需物流发货」。
纯 Python + SQLite，自带 Web 管理后台，不需要 MySQL / Redis。

也可以接上 **new-api + new-api-cost** 全自动开卡：按订单实付金额建对应额度的 Key，
再把 Key 换成卡密发给买家 —— 原来手工做的三步全部省掉。

如果买家嫌「每单都换 Key」麻烦，可以改用**充值模式**：第一次买时自动开一个 Key 并绑定，
之后每单直接把额度充到同一个 Key 上（不再换 Key、也不用卡密站）。发货模式按
**商品 / 规格**单独配置，同一个后台可以混着用。

## 功能

- **扫码登录**：网页后台直接出二维码，手机扫一下就行，不用再从 F12 抠 Cookie（也保留手工粘贴）。
- **付款即发货**：识别闲鱼「我已付款，等待你发货」系统卡片，命中规则后立刻发送发货内容。
- **订单轮询兜底**：IM 推送会因为断线/风控漏消息，所以另外定时拉一次「待发货」订单；两条路都靠 `delivered` 去重，不会重复发。
- **快发货**：收到任何 IM 推送就提前叫醒轮询（`XY_ORDER_HINT_POLL_GAP`），订单里已经带了金额就不再查一次详情，买家的会话能复用就不重新建；
  同时待发货订单并行处理（`XY_ORDER_POLL_CONCURRENCY`）。实测「付款 → 收到卡密」通常只要 1~2 秒。
- **按金额发兑换码**（可选）：查订单实付金额 → new-api 生成同额度兑换码 → 卡密站包成卡密 → 发给买家。
- ~~按金额自动开卡~~：卡密站改版后不再接受 API Key，这条已停用（规则会失败并回滚令牌）。
  令牌名按 `买家用户名#订单号` 生成（如 `测试小鱼#2500000000000000003`），方便在 new-api 后台按买家对账。
  买家名取不到时会依次退：会话资料 → 聊天记录 → 订单详情 → 「买家」，拿到真名后连历史流水一起回填。
- **Key 限模型**：新建的令牌默认只允许 deepseek-v4.1-flash（model_limits_enabled 与 model_limits 一起下发），
  买家拿 Key 也调不了别的模型。**模型白名单直接在后台「设置」页改，保存即生效，不用重启、不用改 .env**；
  `.env` 里的 `XY_NEWAPI_MODEL_LIMITS` 只在后台没保存过时作为默认值。
- **按商品配模型**：同一个站点卖不同价位的商品时，可以给每个商品单独指定模型白名单
  （后台「设置 → 按商品指定模型」）。优先级：本商品 > `*` 兜底 > 全局值；没配的商品沿用全局值。
- **多种发货模式**：`upstream` 按订单金额建新 Key 出卡密、`topup` 充值到买家已有 Key、
  `card` 本地卡密池、`text` 固定文案。规则可以按商品 + 规格关键词 / **金额区间**分开配，
  同一件商品的不同价格规格也能走不同策略（后台「发货规则」）。
  闲鱼多规格商品在订单里通常只有成交价、没有 SKU 名称，**金额区间是识别价格档最可靠的方式**。
- **充值到已有 Key**（`topup`）：不再每单换 Key。默认让买家发「之前购买 Key 的订单号」，
  只充那一单对应的 Key —— 已经买过多个 Key 的老客户也能自己选；找不到就回提示让他重发。
  也可以让买家**直接发 Key**（`api_key` 策略）：只认「本站发给他本人」的令牌，
  不是本人的 / 不是本站的都明确拒绝，绝不往别人的 Key 上充钱。
  还可以切成 `auto` 模式：首单自动开新 Key 并绑定，老客户自动认最近一单。
  同一个站点卖多个商品时（比如 deepseek 与 kimi，Key 的模型白名单不同）可以开「只认同商品」，
  防止买家拿另一个商品的订单号来续费、额度充到那一个 Key 上。
  只依赖 new-api，**不需要卡密站**。后台「买家 Key」页可以手工绑定 / 更换 / 解绑、随时刷余额。
- **后台直接聊**：新增「聊天」页，像微信一样按会话看买家的闲鱼私信、直接回复，带未读红点。
  打开会话时按需补拉最近历史；从「发货记录」点某一单的「聊天」，没有会话会自动建一个。
- **新消息 / 新订单提示**：买家来私信、店铺进新订单时，右下角弹气泡 + 提示音，
  左侧「聊天」显示未读总数、「发货记录」挂新单红点，标签页标题也带上 `(N)`；
  授权后页面切到后台还能弹浏览器桌面通知。右上角小铃铛里可以逐项关掉，
  开关和「看到哪一单」都存在本机浏览器里。
- **图片 / 视频**：聊天页可以直接发本地图片和视频。图片先压缩再传闲鱼 CDN；
  视频走网页端的分片上传，自动截第一帧当封面。服务器需要装 `ffmpeg` / `ffprobe`。
- **内置图片库**：常用图片在后台传一次（存在 `data/media`），聊天时点一下就直接发给买家。
- **撤回消息**：自己发出、且在两分钟内的消息可以撤回；聊天页的「撤回」按钮直接调闲鱼 IM 的撤回接口。
- **卡密池**：按商品分池 + 通用池，出库即锁定（`UPDATE ... WHERE status = available`），不会重复发同一张。
- **自动确认发货**：可选调用 `mtop.taobao.idle.logistic.consign.dummy` 完成虚拟商品免物流发货。
- **自动回复**：两条独立的路子 —— **商品自动回复**（买家针对某商品说任何话就回一条）和
  **关键词自动回复**（话里命中关键词才回）。两者都支持商品范围、包含/完全一致/正则匹配、
  「同一会话只回一次」与冷却，规则都在后台「自动回复」页维护；**一条规则里可以配多条
  「关键词 → 回复」**（也可以按「关键词 => 回复」从文本粘贴），不用一个关键词建一条规则。
- **自动评价**：买家确认收货后闲鱼会推「快给ta一个评价吧」的系统卡片，开启后自动给好评
  （只调 rate=1，不会自动给中差评）。文案可配变量，推送漏了还有成交订单轮询兜底；
  已评价的订单会记入评价记录，不会重复调用接口。
- **收消息有两条路**：WebSocket 推送（快）+ 定时拉会话列表（一定有）。闲鱼的推送经常只带
  「某会话有新消息」的未读标记、**不带正文**，只靠推送会出现「自动回复配了但从不触发」。
- **不吃系统代理**：所有出站请求（闲鱼 HTTP / 长连接、扫码、上游接口）一律直连，
  不读 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `WS_PROXY`；挂梯子时不会把正在接单的账号
  一起带走。TUN / 全局模式属于系统路由层，要在代理客户端里给这个进程加 DIRECT，见「代理 / TUN」。
- **防重复**：同一订单号只发一次（数据库唯一索引），另有冷却期兜底。
- **多账号**：每个账号一条独立长连接任务，断线按 5/10/30/60/120 秒退避重连；风控/滑块单独长退避重试，只有真正 Cookie 失效才停下并报错。
- **可观测**：消息流水、发货记录、账号连接状态都能在后台看到。
- **DRY-RUN**：`XY_DRY_RUN=1` 时只打日志不真的发消息，适合先跑通再上线。

## 快速开始

```bash
cp .env.example .env      # 填上游配置，见下一节
./start.sh                # 启动（首次自动建 .venv 并装依赖），打开 http://127.0.0.1:8000/
```

停服务就是 `./start.sh stop` —— **不用再 `ps aux` 找 pid**，见下方「启动与停止」。

打开后台后只有三步：

**第一步 · 登录闲鱼** —— 点「生成二维码」，用手机闲鱼 App 右上角扫一扫，确认后自动保存账号并开始监听私信。
扫不出来就退回到「手工粘贴 Cookie」（F12 复制整条，必须含 `unb` 与 `_m_h5_tk`）。

**第二步 · 配置发货规则** —— 选一种发货模式（「充值到买家已有 Key」不换 Key；
「按订单金额建新 Key」每单发一张卡密），商品 ID 可以直接从「我的在售商品」下拉里选，
保存前下面会实时显示「订单 ¥10 → $10 额度」这种换算预览。

**第三步 · 试一单** —— 用另一个号拍下付款，看「发货记录」里状态是不是 `delivered`。
充值模式默认要求买家提供旧订单号；自己试单时如果没有旧订单，先把规则切成「自动」，
或者用另一笔已经发过货的订单号来试。

> 建议第一次把 `XY_DRY_RUN=1` 打开跑一单。DRY-RUN 只打日志，连订单查询都不做，更不会真去建 Key。

**可选 · 配自动回复** —— 后台「自动回复」页有两块：

- **商品自动回复**：买家针对这个商品发来任何一句话就回一条，常见用法是「在的，拍下自动发货」；
- **关键词自动回复**：买家说的话里命中关键词才回，常见用法是把「发货」「多久」「怎么用」
  映射到各自的答复。

一条规则里可以配多条回复：给同一个商品把所有常见问题（发货、怎么用、售后…）
一次配完，买家命中哪条就回哪条。

自动回复和发货互不干扰：付款卡片不会触发自动回复（那一单该走发货），
发货成功也不会被自动回复打断。

## 启动与停止

整套服务只有一个入口：**`start.sh`**。不写子命令就是启动：

```bash
./start.sh                # 启动（首次自动建 .venv + 装依赖）；等端口真的通了才返回
./start.sh stop           # 停止（SIGTERM，15 秒不退才 SIGKILL）
./start.sh restart        # 重启（改了代码 / 配置后用）
./start.sh status         # 在不在跑、pid、地址、运行多久
./start.sh logs -f        # 跟着看日志（Ctrl-C 只退出查看，服务照跑）
./start.sh fg             # 前台运行，日志打在终端（调试用）
```

**为什么不用 `python main.py &`** —— 前台跑当然也行（`./start.sh fg`），
但后台运行有几个坑，`start.sh` 都替你挡了：

| 场景 | 裸跑 `python main.py &` | `./start.sh` |
| --- | --- | --- |
| 忘了 pid | 得 `ps aux \| grep main.py` | `./start.sh status` 直接告诉你 |
| 杀掉后不确定死没死 | 不知道，可能还在跑 | 等到**端口真的释放**才返回 |
| 重复启动两个实例 | 两个 Worker 抢同一个 Cookie，闲鱼报「被挤爆啦」 | 检测到已在运行就**拒绝启动** |
| 机器重启后遗留 pid | 照着旧 pid `kill` 可能**误杀别人的进程** | 核对命令行确实是本项目的 `main.py`，对不上就不动它 |
| 关掉终端 / SSH 断开 | 进程可能被 SIGHUP 带走 | 独立会话运行，不受影响 |
| 启动失败 | 只在终端滚过一段报错 | 直接打印**日志最后几行**，一眼看到错在哪 |
| 换机器 / 新克隆 | 要先手动建 venv、装依赖 | 首次运行自动建 `.venv` 并装依赖（pip 缺失时自动改用 uv） |

实现上就三件事：`data/app.pid` 里存 pid + 命令行 + 端口（只用于「下次核对是谁」，**不存任何凭据**）；
停止走 SIGTERM → 超时 SIGKILL → 等端口释放；启动前确认没有实例在跑、端口也没被别人占。

> 想让服务开机自启 / 崩溃自动拉起，还是用 systemd 最稳（见下方「用 systemd 常驻」），
> `start.sh` 负责日常启停和排查，两者不冲突。

### 用 systemd 常驻

```ini
[Unit]
Description=xianyu-auto-reply
After=network-online.target

[Service]
Type=simple
User=你的用户名
WorkingDirectory=/path/to/xianyu-auto-reply
ExecStart=/path/to/xianyu-auto-reply/.venv/bin/python main.py
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`systemctl enable --now xianyu-auto-reply` 之后用 `systemctl status|restart` 管理，
日志走 `journalctl -u xianyu-auto-reply -f`。注意：这时候**别再用 `./start.sh start`**，
两套东西同时管一个服务会互相打架。

## 接上 new-api + new-api-cost（全自动开卡）

> ⚠️ **这一节已经过时。** 卡密站 2025-10 改版成「额度兑换码商店」后，
> 不再接受 API Key（连 `sk-` 都会明确拒收），所以「建 Key → 灌卡密」这条路
> **现在走不通了**：规则会失败并回滚令牌，订单详情里会写「额度兑换码不能是 API Key」。
> 卖 Key 请改用「充值到已有 Key」模式，卖额度请用 **兑换码模式**（见下面那一节）。
> 下面的流程图只作为历史说明保留。

你原来的流程是手工三步：新建对应金额的 Key → 导入卡密站生成卡密 → 把卡密发给买家。
配置好后这三步由程序完成，顺序不变：

```
闲鱼订单实付 ¥10.00
  └─ 换算额度：10 ÷ 1 = $10.00          （XY_CNY_PER_USD=1，1 元 = 1 美元）
      └─ new-api  POST /api/token/      建一个额度 $1.37、名为「买家用户名#订单号」的令牌
          └─ 取回 sk-xxx
              └─ 卡密站 POST /api/admin/cards  用这个 Key 生成卡密（名称同样是「买家用户名#订单号」）
                  └─ 卡密发到闲鱼私信 + 自动点「无需物流发货」
```

### 前提

- **new-api** 站点可访问，账号能在后台「令牌」页新建令牌；
- **卡密站（new-api-cost）** 的 `ADMIN_TOKEN` 已填（或用后台账号密码登录）；
- 卡密站的 `CARDS_SECRET` 已备份 —— 它丢了以后卡密就换不出 Key。

### 配置

```bash
# 上游一：new-api
XY_NEWAPI_BASE_URL=https://api.lumorian.org
XY_NEWAPI_ACCESS_TOKEN=          # 登录响应里的 access_token，或留空用下面两个
XY_NEWAPI_USERNAME=
XY_NEWAPI_PASSWORD=
XY_NEWAPI_GROUP=                 # 令牌落在哪个分组，留空用默认
XY_NEWAPI_TOKEN_PREFIX=           # 可选前缀；不填时令牌名就是「买家用户名#订单号」
XY_NEWAPI_MODEL_LIMITS=deepseek-v4.1-flash   # 仅作默认值；改限制建议用后台「设置」页（留空 = 不限）

# 上游二：卡密站
XY_CARDSHOP_BASE_URL=https://shop.lumorian.org
XY_CARDSHOP_ADMIN_TOKEN=

# 换算（1:1 是有意为之：订单 10 元 → $10 额度）
XY_CNY_PER_USD=1
XY_MAX_ORDER_CNY=200             # 单笔上限，防标错价被刷；0 = 不限
```

> **模型限制只作用于新建的 Key。** 之前已经发出去的旧 Key 不会自动补上限制，
> 需要在 new-api 后台「令牌」页逐个编辑（勾选「模型限制」并填 deepseek-v4.1-flash），
> 或者让买家换新 Key。

> `quota_per_unit`（$1 = 多少 quota）会实时读 `/api/status`，读不到才用兜底值 500000。
> 你这台站是 500000，所以 ¥10 → $10 → `remain_quota = 5000000`。

### new-api 凭据怎么拿（两个值，别漏第二个）

需要用 **access_token** 和 **user_id** 两个值，原因见下。

**① user_id（New-Api-User）**

new-api 0.13.x 起，所有 `/api/*` 后台接口都强制要求请求头带 `New-Api-User: <你的用户id>`，
少这个头直接 401 —— 报错是 `Unauthorized, New-Api-User header not provided`。

拿法（任选一）：

- 登录 <https://api.lumorian.org> → 右上角头像 → 个人设置，页面上能看到用户 ID；
- 或直接看数据库 `SELECT id FROM users WHERE username='你的用户名';`；
- 或 F12 → Network → 任意一个 `/api/user/self` 请求 → 看请求头里的 `New-Api-User`。

**② access_token（系统访问令牌）**

这是**长期有效**的凭据（不像登录态那样过期），正是给脚本用的：

1. 登录 <https://api.lumorian.org>；
2. 进「个人设置」（右上角头像 → 个人设置）；
3. 找到 **「系统访问令牌」/「访问令牌」/ Access Token** 那一栏；
4. 点「生成」/「重置」按钮，复制出来的那串就是。

> 它是 base64 风格的随机串（约 40 字符），**不是** `sk-` 开头的 API Key。
> `sk-` 那些是「令牌」页里给客户端调模型用的，跟这个不是一回事，别搞混。

也可以直接调接口生成（用浏览器登录态）：

```bash
# 在浏览器已登录的前提下，从 F12 → Network 复制 Cookie，然后：
curl -X GET 'https://api.lumorian.org/api/user/token' \
  -H 'New-Api-User: <你的user_id>' \
  -H 'Cookie: <浏览器Cookie>'
# 返回 {"success":true,"data":"<access_token>"}
```

**③ 其实还有个更省事的办法**

不填 access_token，直接填账号密码：

```bash
XY_NEWAPI_USERNAME=你的用户名
XY_NEWAPI_PASSWORD=你的密码
```

程序登录时会自动从响应里拿 user id 和 access_token，**这两个都不用你填**。
代价是把密码写进 `.env`（文件权限设 600），并且每次启动多一次登录请求。

> ⚠️ 账号模式（建号 / 充到账号）还要给这枚令牌勾上「管理 → 用户 查看 + 编辑」，
> 否则所有账号相关调用都会 403。详见下面「账号模式」那一节。

> ⚠️ 光有 access_token 是**没法自动补 user_id** 的 —— 因为查用户信息本身就要 New-Api-User 头。
> 所以要么用账号密码，要么两个值都手工填。

### 卡密站凭据

`https://shop.lumorian.org` 已内置为默认地址。凭据二选一：

- `XY_CARDSHOP_ADMIN_TOKEN`：卡密站 `.env` 里的 `ADMIN_TOKEN`（默认是空的，需要你填一个）；
- 或 `XY_CARDSHOP_USERNAME` / `XY_CARDSHOP_PASSWORD`：后台管理员账号密码。

> 卡密站首次部署后必须先登录 `/admin` 改掉 `admin`/`admin`，
> 否则所有业务接口返回 428「首次登录必须先修改密码」。

### 上线前先自查

管理后台「发货规则」上方会显示一行状态：

- ✅ **上游已接通** —— new-api 和卡密站都齐了，「兑换码」和「充值到已有 Key」都能用；
- ℹ️ **new-api 已接通（卡密站未配置）** —— 充值模式可用，兑换码模式不可用；
- ⚠️ **上游未配置** —— 上面那些环境变量还缺，两种模式都不能用。

再打开 `XY_DRY_RUN=1`（只打日志不真发，**也不会真的去建 Key / 充值**），用测试账号拍一单看日志，
确认金额/额度换算对了再关掉。

### 失败时会怎样

| 情况 | 行为 |
| --- | --- |
| 查不到订单金额，且规则填了固定额度 | 用固定额度继续发货 |
| 查不到订单金额，也没填固定额度 | 不发，记 `upstream_failed`（原因：查不到订单金额） |
| 金额超过 `XY_MAX_ORDER_CNY` | 不发，记 `upstream_failed`（原因：订单金额超上限） |
| new-api 建令牌失败 | 不发，记 `upstream_failed` |
| 令牌建好了但卡密生成失败 | **自动删除刚建的令牌**，不发，记 `upstream_failed` |
| Key/卡密建好了但还没发送 | 记 `provisioned`；进程重启或发送失败后**复用同一份卡密**，不重新开 Key |
| 发送被服务端明确拒收 | 记 `send_failed`；本地卡密回库存，上游卡密保留在记录里供重试复用 |
| 发送 ack 超时 / 连接中途断开 | 记 `send_unknown`；卡密不退回、**不自动重发**，到闲鱼聊天里人工核对 |
| 发送前落库后进程中断 | 启动时把残留的 `sending` 转成 `send_unknown`；同样不退卡、不自动重发 |

```sql
-- 事后查事故：看看哪些订单没发出去
SELECT created_at, order_id, status, detail FROM orders WHERE status != 'delivered';
```

### Key 能调哪些模型（后台直接改）

打开后台左侧「**设置**」页 → **Key 模型限制**：

1. 填允许的模型，逗号 / 空格 / 换行分隔都行（中文逗号也可以），例如 `deepseek-v4.1-flash, deepseek-v4.1`；
2. 点「保存设置」——**立刻对新订单生效，不用重启、也不用改 .env**。

页面会实时显示「保存后新 Key 会变成这样」，也就是实际下发给 new-api 的
`model_limits_enabled` / `model_limits`。

- **留空 = 不限制模型**（买家拿 Key 能调任意模型）。这种状态顶部会挂一条红色警告，规则页的横幅也会标红。
- 保存过的值存在数据库 `app_config` 表里，**优先级高于 `.env` 的 `XY_NEWAPI_MODEL_LIMITS`**；
  `.env` 里那个值只在后台从没保存过时作为默认值（老部署升级上来行为不变）。
- 只影响**之后新建**的 Key。已经发出去的旧 Key 是建令牌时就写死在 new-api 里的，
  要收紧 / 放开都得回头改令牌（下面有脚本）。
- 这里只存运营参数（模型白名单）。access_token、密码这类凭据仍然只从 `.env` 读，不会写进数据库。

> 注意：这道保护依赖 new-api 自己的 `model_limits`，改了要确认 new-api 版本支持
> （0.13.x 需要同时带 `model_limits_enabled: true`，本工具已经这么发了）。

### 按商品指定模型（不同商品发不同模型）

同一个 new-api 站点上卖「月卡」和「季卡」时，经常希望月卡只能调便宜的模型、
季卡可以调更多。后台「**设置 → 按商品指定模型**」就是干这个的：

| 配置 | 生效范围 |
| --- | --- |
| 商品 `900052644277` → `deepseek-v4.1-flash` | 只对这个商品生效 |
| 商品 `*` → `deepseek-v4.1-flash, deepseek-v4.1` | 没单独配置的商品都走这条 |
| 不配 | 用上面的全局「Key 模型限制」 |

优先级：**本商品 > `*` 兜底 > 全局值**。每一行都有「允许的模型」和备注；
**留空 = 这个商品不限制模型**（有意放开，不是「用全局值」）。

- 保存后立刻对之后的新订单生效，不用重启；已经发出去的旧 Key 不受影响。
- 只在**建新 Key** 时使用（`upstream` 模式，或 `topup` 模式的首单）；本地卡密池 / 固定文案不建 Key，
  给已有 Key 充值也不会改动它的模型限制。
- 发货规则页的「额度策略」下面会直接显示这一单实际会用哪一组模型（本商品 / `*` 兜底 / 全局）。
- 接口：`GET /api/item-models`、`POST /api/item-models`、`PUT /api/item-models/{id}`、`DELETE /api/item-models/{id}`。
  `POST` 同一个商品会就地更新，不会报重复。

#### 把已经发出去的 Key 批量放开（维护脚本）

决定「以后所有 Key 都能用 deepseek + kimi」之后，**老 Key 不会自动跟着变**——
模型白名单是建令牌时写死的。用这个脚本把存量令牌改一遍（默认只预览）：

```bash
.venv/bin/python scripts/open_models.py --models "deepseek-chat,kimi-k2"          # 预览
.venv/bin/python scripts/open_models.py --models "deepseek-chat,kimi-k2" --apply  # 真改
```

- 默认取**并集**：只把缺的模型加进去，不动令牌原有的其它模型（少写一个模型名等于把
  已经卖出去的权限收回去）。要强行对齐用 `--exact`。
- 不带 `--models` 时用后台「设置」里的全局白名单，也就是「新 Key 会拿到的那一组」。
- `model_limits` 没启用的令牌（= 不限模型）直接跳过，不会被改窄。
- 改之前会先读完整令牌记录、只改这两个字段再写回，额度 / 分组 / 过期时间都不动。
- 只处理令牌名包含 `--keyword` 的那些可以缩小范围，例如 `--keyword "#2503"`。

## 充值到买家已有 Key（不换 Key）

买家反馈「每单都换 Key，客户端要重新填」时，把商品规则的模式改成 `topup` 就行：

```
买家拍下「充值」商品并付款
  └─ 私信提示：请发你之前购买 Key 的那笔订单号
      └─ 买家发来旧订单号 → 校验「这单确实是本人、已发货、有 Key」
          ├─ 有：new-api 读令牌 → remain_quota += 换算额度 → 原样写回
          │       └─ 私信发「已充值 + Key + 最新余额」+ 自动点「无需物流发货」
          └─ 没有：回「没有找到这个订单号对应的 Key」，订单挂起等买家重发
```

**只依赖 new-api**，不需要卡密站，所以只配了 `XY_NEWAPI_*` 也能用。

### 怎么决定充到哪个 Key

规则里有一个「怎么确定要充值的 Key」，三种策略：`order_id`（买家发旧订单号）、
`api_key`（买家直接发 Key）、`auto`（自动选）。

#### `order_id`：买家发旧订单号（默认，推荐）

适合**之前已经买过多个 Key** 的客户 —— 买家自己指定要充哪一笔订单对应的 Key：

1. 买家拍下充值订单后，程序先发一条提示，让他发「之前购买 Key 的订单号」；
2. 买家发来订单号后，程序校验：这笔订单**属于这个买家**、状态是 `delivered`、并且能对上令牌；
3. 对上了就只充那一笔订单对应的 Key；找不到就回一条「没有找到这个订单号对应的 Key」，
   订单停在 `awaiting_key`，买家可以重新发；
4. 早期订单没记令牌 id 时，按令牌名里的 `#订单号` 反查（老客户不用重买一次）；
5. 同一个买家有多笔等待中的充值订单时，按购买顺序逐笔处理，成功后自动提示下一笔。

提示文案和「找不到」文案都可以在规则里改，留空用内置默认值。买家发来的订单号
只认「本人 + 已发货」的订单，**不会把别人的订单号对应的 Key 充给当前买家**。

> **跨商品保护（可选，默认关）**：规则里把「允许拿另一个商品的旧订单来充值」选成「不允许」
> （`topup_item_scope=item`）后，只有**同一个商品**的旧订单才能当充值目标。
> 买家拿 kimi 那笔订单来续 deepseek 时，程序会回「订单 xxx 不是这个商品的订单」，
> 订单停在 `awaiting_key` 等他发对本商品的订单号，**不会**把额度充到 kimi 的 Key 上。
> 早期没记商品 ID 的订单仍然放行（没有证据就按老行为走），不会把老客户挡在门外；
> 默认是 `any`，和以前的「任意已发货订单都能当充值目标」完全一样。

> 买家如果比订单轮询早几秒发来旧订单号，程序会在内存里短暂记住 2 分钟，
> 等充值订单出现时直接用；超过这个窗口就按正常流程重新提示。

#### `api_key`：买家直接发 Key（最省事）

买家不用翻订单号，直接把 Key 发过来：

```
买家拍下充值商品并付款
  └─ 私信提示：请把要充值的 Key 发给我（sk- 开头那一整串）
      └─ 买家发来 Key → 核对「这是本站的 Key，而且是发给他本人的」
          ├─ 是：new-api 读令牌 → remain_quota += 换算额度 → 回「已充值 + Key + 余额」
          ├─ 不是他买的：回「这个 Key 不是你在本店购买的」→ 订单继续等
          └─ 不是本站的：回「这个 Key 不在本站的中转站里」→ 订单继续等
```

核对顺序（从便宜到贵，全都对不上就不充）：

1. 「买家 Key」页里这个买家的绑定；
2. 他自己的历史订单里发出去的那串 Key（充值模式的订单 `card_code` 存的就是 Key 明文）；
3. 他名下出现过的令牌，逐个读明文 Key 比对；
4. 本站令牌列表：列表直接带明文的当场比；**打码的版本**按「本人名下 → 令牌名像他 →
   其它」的顺序，逐个用单令牌接口读明文核对；
5. 列表完全拿不到（权限 / 站点异常）时才退回「按 Key 反查」。

几个细节：

- **只认本人**：两种认法 —— 绑定表 / 历史订单里记过这个令牌 id，或者令牌名里的
  `#订单号` 是这个买家已发货的单（早期订单没记令牌 id，但名字里有）。
  两种都对不上就绝不充，宁可让客服手工处理。
- **打码的 Key**（`sk-ab12…wxyz`）单独提示「请长按复制完整 Key」，不会当成失败重试。
- 同一买家 10 分钟最多试 5 次 Key：每次核对都可能读令牌 / 翻列表，防止有人刷屏打上游。
- 买家比订单轮询早一步发 Key 也没关系：核对通过的令牌在内存里记 2 分钟，订单出现直接充。
- 充值失败后轮询重试会复用已经核对过的令牌（记在订单的 `api_key_id` 上），
  不会让买家再发一遍 Key。
- **列表把 Key 打码也不影响**：单令牌接口 `POST /api/token/{id}/key` 仍能拿到明文，
  所以第 4 步会按「名字像他 → 其它」的顺序逐个核；给整轮核对设了 8 秒上限，
  站点令牌特别多、到点还没认出来时才会回「暂时没法按 Key 充值」。

> 这个策略和「一个 Key 通吃多个模型」是绝配：买家不用记哪笔订单对应哪个 Key，
> 手上那串 Key 就是充值目标；`topup_item_scope`（只认同商品）对它没有意义，不用开。

#### `auto`：自动选 Key（适合首单 / 只有一个 Key 的客户）

按顺序找，前一步没有再走下一步：

1. 后台「买家 Key」页手工绑定的那一条（**不会被自动绑定覆盖**）；
2. 之前自动绑定过的记录（首单开的 Key / 上一单的 Key）；
3. 买家最近几单 `delivered` 里记下的令牌；早期订单没记令牌 id 时，按令牌名里的
   `#订单号` 反查；
4. 都没有：按规则里的「买家还没有 Key 时」处理 ——
   - **自动开一个新 Key 并绑定**（首单体验和原来一致）；
   - **不发货**（记 `topup_failed`，去后台绑定后订单轮询会自动重试）。

> 首次购买、手上还没有旧订单的买家，用 `auto` 策略（或者单独发一个「首单」商品）；
> `order_id` 策略是给老客户用的，他们没有旧订单号时会被提示「没有找到 Key」。

> 开了「只认同商品」时，上面的顺序也按商品过滤：自动绑定的 Key 要先证明是在这个商品上
> 发过的才用，历史订单也只在这个商品里找（更早买过本商品仍然认得出来）；
> 后台**手工**绑定的照用 —— 那是运营的明确意图，只打一条告警日志。

后台「买家 Key」页可以按令牌 ID 绑定，也可以直接粘贴 `sk-...`（会去 new-api
令牌列表里反查）。列表只显示打码后的 Key；余额可以随时手动刷新。
**`order_id` 策略不读这里的绑定**，以买家发来的旧订单号为准；这个页面主要配合
`auto` / `api_key` 策略（`api_key` 会先看这里，命中就直接充），
或者处理「旧订单记录缺失、只能手工指定」的老客户。

接口：`GET/POST /api/buyer-keys`、`PUT/DELETE /api/buyer-keys/{id}`、
`POST /api/buyer-keys/{id}/refresh`、`GET /api/newapi/tokens?keyword=`。

### 发货文案

充值模式支持额外的变量：

| 变量 | 含义 |
| --- | --- |
| `{key}` | 买家原来那个 Key（读不到明文时是打码值） |
| `{balance}` | 充值后的余额（站点展示货币） |
| `{quota}` | 本单充值的额度 |
| `{card}` | 和 `{key}` 相同（兼容旧文案） |

文案留空时用一段默认提示。**已有 Key 的模型限制不会被改动** —— 只有首单新建的 Key
才按「设置 → Key 模型限制 / 按商品指定模型」下发。

### 失败时会怎样

| 情况 | 行为 |
| --- | --- |
| 买家还没发旧订单号（`order_id` 策略） | 记 `awaiting_key`，轮询会跳过这一单，等买家发订单号 |
| 买家发的订单号不是本人的 / 订单没有 Key | 回「没有找到这个订单号对应的 Key」，订单继续停在 `awaiting_key` |
| 买家发的是**另一个商品**的订单号，且规则开了「只认同商品」 | 回「订单 xxx 不是这个商品的订单」，订单停在 `awaiting_key`、detail 写明「属于另一个商品」；**不充值** |
| 买家发的 Key 不是他买的（本站有、归属不符） | 回「这个 Key 不是你在本店购买的」，订单停在 `awaiting_key`；**不充值** |
| 买家发的 Key 不在本站 | 回「这个 Key 不在本站的中转站里」，订单停在 `awaiting_key`；建议他改发订单号 |
| 买家发的是打码后的 Key | 回「请长按复制完整 Key」，订单停在 `awaiting_key` |
| Key 认到了令牌，但令牌被删 / 换代了 | 回「这个 Key 对应的令牌读不到」，订单停在 `awaiting_key` |
| 提示买家发订单号的消息没发出去 | 记 `topup_failed`，轮询下一轮会再试（同一单提示有 10 分钟冷却） |
| 找不到已绑定 Key，`auto` 模式选了「不发货」 | 记 `topup_failed`，绑定后同一单会自动重试 |
| new-api 明确拒绝（令牌禁用 / 过期 / 额度换算为 0） | 记 `topup_failed`，修好后可重试 |
| 充值请求已发出但回包超时 / 502 / 非 JSON | 记 `topup_unknown`，**不自动重试**，去 new-api 后台核对余额 |
| 充值成功、消息发送失败 | 记 `send_failed`，下一轮复用同一份结果重发，**不会重复充值** |
| 进程在充值过程中被杀 | 启动时把残留的 `topping_up` 转成 `topup_unknown`，等人工核对 |
| 进程在等买家发旧订单号时重启 | 启动时把 `awaiting_key` 转回 `topup_failed`，轮询会重新提示一次 |

## 兑换码模式：卖 new-api 兑换码（走卡密站，推荐用于新商品）

> 一句话：机器人**生成 new-api 兑换码** → **灌进一张卡密** → 聊天里只发卡密串。
> 买家去卡密站兑换拿到兑换码，再登录站点「钱包 → 兑换额度」。
> 机器人**不碰任何人的账号**：不需要密码、不需要判断归属、不需要二次确认。

> 卡密站 2025-10 改版后是 **「一个兑换码 = 一张卡密」**：卡密里只有兑换码本身，
> 放不下自定义文本（旧接口的 `key` / `count` / `maxRedeems` 全部作废）。
> 所以兑换步骤写在**发给买家的消息**里，而不是塞进卡密。

### 需要准备什么

1. new-api 令牌勾上 **管理 → 兑换码 → 查看 + 编辑**（`redemption:read` / `redemption:write`）；
2. 卡密站配好（`XY_CARDSHOP_*`）—— 聊天里发的卡密是从这里出的；
3. 两条路都通了，「发货规则」页顶部的横幅才会是「上游已接通」。

走这条路**不需要**「用户」权限 —— 那套是账号模式（开号 / 充到账号）用的。
只卖兑换码，只勾兑换码即可。

### ⚠️ 上线前必须先做的事

new-api 有一条合规闸门：**没在后台确认过「支付 / 兑换 / 订阅合规条款」时，
生成兑换码会直接失败**，报错是：

> Payment, redemption, subscription, and invitation reward features are disabled.
> The administrator must confirm compliance terms before enabling them.

去 new-api 后台（超管账号）同意那条条款，之后 `POST /api/redemption/` 才可用。
你之前从来没在后台手动发过兑换码的话，几乎一定会踩到 —— 机器人会把这句英文
翻成中文提示写进订单详情。

### 买家看到的两层

1. **聊天里**：卡密串 + 卡密站地址 + 兑换步骤（具体去哪个页面的哪一栏）。
2. **卡密站兑换后**：只有那串 new-api 兑换码。

这样兑换码不会躺在聊天记录里被转发，卡密站仍然负责「一次性展示 / 留底 / 客服补发」。

### 怎么配

「发货规则」→ 新建规则（商品 ID 填你新开的兑换码商品）→ 发货模式选「兑换码」：

| 字段 | 说明 |
| --- | --- |
| 金额倍率 / 固定额度 | 额度 = 订单金额 ÷ 汇率 × 倍率；填了固定额度就忽略订单金额 |
| 金额区间 | 可选，用来区分同一商品的不同价格档 |
| 兑换码有效期（天） | 0 = 永不过期（new-api 用 0 表示不过期，和令牌的 -1 不一样） |
| 发货文案 | **发给买家的消息**：可用 `{card}`（卡密）、`{shop_url}`、`{login_url}`、`{quota}` `{amount}` `{buyer}` |

留空就用内置默认（卡密 + 卡密站地址 + 兑换步骤）。注意：兑换码本身**不会**
出现在聊天里，模板里也拿不到它 —— 它只在卡密里。

> 卡密站自己的兑换页已经是「额度兑换码」口径，会提示去站点「钱包 / 充值」里兑换 ——
> 所以聊天里那句可以写得简单些，两边不会互相打架。

### 后台里长什么样

new-api 的兑换码名称限 **20 个字**，而闲鱼订单号本身就有 19 位，所以这边不沿用
卡密那套「买家名#完整订单号」，而是 **昵称前 6 个字 + # + 订单号后 8 位**
（例如 `买家小王#00000001`）。在后台「兑换码」页按名称搜订单号尾部就能对上账。

### 失败时会怎样

| 情况 | 行为 |
| --- | --- |
| 生成兑换码失败（权限不够 / 合规没确认 / 上游 5xx） | 记 `redeem_failed`，**不发消息**，轮询下一轮自动重试 |
| 码生成好了、卡密站失败 | 记 `redeem_card_failed`，码写进订单的 card_code；下一轮**复用同一个码**重试卡密站，不会每 30 秒往 new-api 灌一个孤儿码 |
| 卡密建好了、消息发送失败 | 记 `send_failed`，**复用同一张卡密**重发，不重新生成 |
| 生成请求超时（不知道建没建出来） | 记 `redeem_failed` 并重试；最坏情况是后台多出一个没人知道的码 |
| 进程在发送过程中被杀 | 记 `send_unknown`，不自动重发，等人工核对 |

> 「多出一个孤儿码」不会亏钱：**生成兑换码不扣任何人的额度**，只有被兑换时才给
> 买家加额度。真有孤儿码，去 new-api 后台「兑换码」页删掉即可。

接口：`POST /api/redemption/`、`GET /api/redemption/`。

## 账号模式：新用户发卡密换账号 / 老用户直接充到账号

> 和上面的「充值到已有 Key」是两条独立的链路。账号模式的额度加在**账号**上，
> 买家拿账号密码登录 new-api 自己建 Key；老链路是把额度加在某一个**令牌**上。
>
> **如果你只是想让老客户续额度，优先用上面的「兑换码模式」**：不用建号、不用存密码、
> 不用判断账号归属，机器人也不碰任何人的账号。这一节保留给「连账号一起卖」的场景。

### 需要给 new-api 令牌什么权限

机器人要在 new-api 上「查账号 / 建账号 / 加额度」，所以手里那枚访问令牌
必须是**管理员账号**签发的，并且勾上：

| 分组 | 权限 | 勾什么 |
| --- | --- | --- |
| 管理 | 用户 | **查看 + 编辑** |

对应三个接口：`GET /api/user/search`（查人）、`POST /api/user/`（建号）、
`POST /api/user/manage`（`action=add_quota` 加额度）。

**不需要**给的：兑换码、充值与订阅管理、模型、部署、日志、分组、审计日志，
以及最危险的渠道管理 / 查看渠道密钥 —— 一项都别勾。

> `用户-编辑` 同时意味着能重置任何普通用户的密码、能停用 / 删除用户。
> 建议**单开一枚专用令牌**只勾这一项，配到 `XY_NEWAPI_ACCESS_TOKEN`，
> 不要在原令牌上叠加。

用账号密码登录（`XY_NEWAPI_USERNAME` / `XY_NEWAPI_PASSWORD`）时权限跟着账号走，
不用额外勾选，但账号本身得是管理员。

### 买家看到的过程

1. **下单付款** → 机器人先问一句：「你之前在本站注册过账号吗？」
2. **新用户**回「没有」→ 机器人请他定一个账号名 → 建号（密码随机生成）→
   加额度 → 把「账号 / 密码 / 登录地址」灌进一张卡密发给他 →
   买家去 `shop.lumorian.org` 兑换查看。
3. **老用户**直接发账号名 → 机器人回显「账号 xxx（当前余额 ¥y），确认充值吗？」
   → 买家回「确认」→ 加额度 → 发货文案里带账号名和新余额。
4. 之后这个买家再下单，**不再询问**，直接充到已绑定的账号。

账号名会被校验：3~20 位、字母或数字开头、只能含字母数字下划线和减号
（new-api 用户名最长 20 位，中文名在登录页和卡密里都不好处理）。被占用会让他换一个。

### 怎么配

「发货规则」→ 新建规则 → 发货模式选「账号模式」。三个文案都可以留空用内置默认：

| 字段 | 作用 | 可用变量 |
| --- | --- | --- |
| 收到订单后先问「有没有账号」 | 第一条消息 | `{buyer}` `{order_id}` `{amount}` `{quota}` |
| 老用户充值前的确认回显 | 回显账号和余额，等一句「确认」 | `{username}` `{balance}` `{quota}` `{login_url}` |
| 卡密内容 | 买家在卡密站兑换后看到的东西 | `{username}` `{password}` `{login_url}` `{quota}` |
| 发货文案 | 发货消息本身（新号 / 老号共用） | 除上面这些还有 `{card}` |

金额倍率 / 固定额度 / 金额区间 / 自动确认 和上游模式完全一样：额度 =
订单金额 ÷ 汇率 × 倍率。

后台「买家账号」页可以手工绑定（按账号名或账号 id）、刷新余额、解绑；
**开号时绑定会自动建立**，后台手工绑定的不会被自动覆盖。「复制密码」会把
账号密码（以及还没兑换的卡密）塞进剪贴板 —— 买家把卡密弄丢时靠它售后。

### 失败时会怎样

| 情况 | 行为 |
| --- | --- |
| 买家还没回「有没有账号」 | 记 `awaiting_account`，轮询跳过，等买家回话 |
| 买家回了「没有」，在等账号名 | 记 `awaiting_username`；名字不合法 / 被占用都会再问一次 |
| 老用户账号查不到 | 回「没有找到账号 xxx」，订单停在 `awaiting_account` |
| 老用户还没回「确认」 | 记 `awaiting_confirm`，不充值 |
| 建号失败（名字刚被抢 / 上游报错） | 记 `account_failed` 并请买家换一个名字；**不会**充到别人账上 |
| 加额度请求已发出但回包超时 / 502 | 记 `topup_unknown`，**不自动重试**，去 new-api 后台核对余额 |
| 额度加好了、卡密站挂了 | 仍按成功发货，直接把账号密码发给买家（卡密站只是展示凭证） |
| 额度加好了、消息发送失败 | 记 `send_failed`，下一轮复用同一份结果重发，**不会重复加额度** |
| 买家连点两次「确认」 | 第二次看到订单已不是等待状态，直接跳过 |
| 进程在加额度过程中被杀 | 启动时把残留的 `topping_up` 转成 `topup_unknown`，等人工核对 |

> 卡密站 `redeem` 页面通篇写的是「API Key / Base URL / 模型 / 查余额」。
> 账号模式下卡密里装的是账号密码，最好把那几处文案改掉，否则买家拿到会一脸问号
> （功能不受影响：余额块在探测失败时会自动隐藏）。

接口：`GET/POST /api/buyer-accounts`、`PUT/DELETE /api/buyer-accounts/{id}`、
`POST /api/buyer-accounts/{id}/refresh`、`GET /api/buyer-accounts/{id}/secret`、
`GET /api/newapi/users?username=`。

## 发货规则怎么配

| 字段 | 说明 |
| --- | --- |
| 商品 ID | 目标商品 ID；`*` 为通配规则。有商品专属规则时优先用它 |
| 规格关键词 | 可选。匹配订单里的 SKU / 商品标题文本，逗号 / 分号分隔；只有平台返回了这些文本才有效 |
| 金额区间 | 可选。最低 / 最高金额（元，含边界），0 = 不限。用于同一商品的不同价格规格（如 ¥1 / ¥5 / ¥10） |
| 模式 | `redeem` 兑换码（生成 new-api 兑换码 → 灌进卡密 → 发卡密，见上文）；`account` 账号模式（问有没有账号 → 开号发卡密 / 充到已有账号）；`topup` 充值到买家已有 Key（不换 Key）；`upstream` 按订单金额建新 Key 出卡密；`card` 本地卡密池；`text` 固定文案 |
| 发货文案 | 支持变量 `{card}` `{key}` `{balance}` `{buyer}` `{item_id}` `{order_id}` `{date}` `{amount}` `{quota}`；账号模式另有 `{username}` `{password}` `{user_id}` `{login_url}`；兑换码模式另有 `{shop_url}` |
| 金额倍率 | 上游 / 充值模式：额度 = 订单金额 ÷ 汇率 × 倍率 |
| 固定额度 | 上游 / 充值模式：填了就忽略订单金额，直接按这个额度建 Key / 充值 |
| 怎么确定 Key | 仅充值模式：`order_id` 买家发旧订单号（默认，适合多 Key 老客户）；`api_key` 买家直接发 Key（只认本人名下）；`auto` 自动选 Key |
| 允许跨商品充值 | 仅充值模式：`any` 买家任意已发货订单都能当充值目标（默认，老行为）；`item` 只认同商品的旧订单 / 同商品发过的 Key（防止拿 kimi 的订单续 deepseek） |
| 催发订单号 / 找不到 Key 的文案 | 仅 `order_id` 策略：收到充值订单后的提示、订单号对不上 Key 时的回复；留空用内置默认 |
| 买家还没有 Key | 仅充值 `auto` 策略：`create` 自动开新 Key 并绑定（默认）；`fail` 不发货，等后台绑定后重试 |
| 自动确认 | 勾选后，文案发完会调用免物流发货接口把订单标记成已发货 |
| 优先级 | 数字越大越优先（同商品多规则时） |

同一商品有多条规则时的优先级：**商品专属 > `*` 兜底**；同一范围内，**命中规格 / 金额条件的规则 >
通用规则**；再按优先级数字。

> **如果规则配了金额区间，但当前拿不到订单金额**，程序会先不选规则（订单轮询拿到金额后重试），
> **不会退回通用规则发错额度**。

### 同一商品不同价格规格怎么配（重点）

闲鱼的多规格商品在订单接口里**不一定返回 SKU 名称**。实测一个「¥1 / ¥5 / ¥10」的商品，
订单里只有：

```json
{
  "itemVO": {"title": "dsv4.1f 1017 一折"},
  "priceVO": {"auctionPrice": "5.00", "totalPrice": "5.00"}
}
```

没有 SKU、规格、属性字段 —— 这时「规格关键词」永远匹配不到，但**成交价是准的**。
正确做法是同一商品建多条规则，用金额区间区分：

| 规则 | 商品 | 金额区间 | 发货 |
| --- | --- | --- | --- |
| 1 元档 | `1094740913216` | 0.99 ~ 1.01 | 固定额度 1（或对应文案） |
| 5 元档 | `1094740913216` | 4.99 ~ 5.01 | 固定额度 5 |
| 10 元档 | `1094740913216` | 9.99 ~ 10.01 | 固定额度 10 |

规则弹窗里有「**读取历史成交价**」按钮：它会从本工具的订单记录里找出这个商品出现过的
实付金额（例如 ¥1 / ¥5 / ¥10）和单数，点一下就能填入区间。新商品还没有成交记录时，
直接手填最低 / 最高金额即可。

> 规格关键词仍然保留：如果订单 / 卡片里确实带 SKU 或商品标题文本，它能用；
> 拿不到文本时建议改用金额区间，而不是指望规格关键词。

典型文案（建新 Key 出卡密）：

```
你好 {buyer}，这是你购买的卡密：
{card}
如有问题请直接回复本消息。
```

典型文案（充值到已有 Key）：

```
你好 {buyer}，已为你充值 {quota} 额度到原来的 Key：
{key}
当前余额 {balance}，直接继续用这个 Key 就行。
```

## 自动回复怎么配

后台「自动回复」页分成两块，规则字段几乎一样：

| 字段 | 说明 |
| --- | --- |
| 规则名 | 自己看得懂就行，日志里会带上；留空自动按第一条关键词生成 |
| 回复类型 | `item` 商品自动回复 / `keyword` 关键词自动回复 |
| 商品 ID | 限定只对某个商品生效；`*` = 所有商品。专属规则优先于 `*` |
| 匹配方式 | `contains` 包含（推荐）/ `exact` 整句完全一致 / `regex` 正则（高级）；这条规则里的回复共用 |
| 回复条目 | 一条规则可以配 1～50 条回复，每条有自己的「关键词 + 回复内容」，见下 |
| 同一会话只回一次 | 勾上后这个会话不会再被**同一条回复**打扰；不勾就按冷却控制频率 |
| 冷却秒数 | 同一买家多少秒内不再回**同一条回复**；0 = 不限 |
| 优先级 | 数字越大越先匹配（同商品多条规则时） |

匹配顺序：**关键词规则 > 商品规则**；同类里商品专属优先于 `*` 通配；
同一条规则里按条目从上到下的顺序，前面的被「会话只回一次 / 冷却」挡住了才会用后面的。

**一条规则配多条回复** —— 点「新建 / 编辑自动回复」，在「回复条目」里：

- 每条回复填自己的关键词（逗号 / 分号 / 竖线 / 换行分隔同义词）和回复内容；
  商品回复没有关键词，配多条时按顺序兜底；
- 点「＋ 加一条回复」继续加，可以上移 / 下移 / 删除；一条规则最多 50 条；
- **每条回复各自去重 / 冷却**：同一个会话里回完「发货」，「退款」那条仍然能回；
- 也可以展开「从文本快速粘贴」，按 `关键词 => 回复内容` 每行一条贴进去；
- 规则名留空会自动用第一条关键词生成；
- 老版本升级上来的规则会各自变成「只有一条回复」的规则；在编辑弹窗里点「加一条回复」
  就能把同商品的几条规则合成一条。也可以直接点规则后面的「合并同商品」，
  一键把同商品、同类型的其它规则并进来（回复记录会保留）；
- 历史命中记录会挂到对应的第一条回复上，升级不会把老会话重新回一遍；
- 接口也支持一次提交多条：`entries: [{keywords, content}, ...]`；老的
  `keywords` + `content` 写法仍然兼容（当成唯一一条）。

```json
{
  "name": "商品 FAQ",
  "kind": "keyword",
  "item_id": "1094740913216",
  "match_type": "contains",
  "entries": [
    {"keywords": "充值, 续费", "content": "充值直接拍下，发新 key"},
    {"keywords": "命中率, 缓存", "content": "实测 96% 以上缓存命中"},
    {"keywords": "人工, 客服", "content": "客服在线 12:00-22:00"}
  ]
}
```

几个必须知道的行为：

- **付款卡片不会自动回复** —— `[我已付款，等待你发货]` 这类系统卡片只走发货，
  不然买家会先收到一句「在的」再收到卡密；
- **系统消息也不回** —— `[你已发货]`、`[请确认微信收款]`、评价提醒这些
  `custom.type != 1` 的消息只记录、不自动回复，避免对着系统提示说「在的」；
- **自动回复是后台任务** —— 带 `XY_AUTO_REPLY_DELAY` 的延迟不会卡住收帧循环，
  紧接着的付款卡片照样立刻处理；
- **发送失败不记入去重** —— 没发出去就不算「回过」，下次买家再问还会回；
- **处理途中出错会重试** —— 消息是「先标记已处理再干活」的（否则推送和拉取会各回一遍），
  所以一旦下游抛异常，程序会**撤销那个标记**，下一轮重新处理；同一条连续失败 3 次后放弃，
  免得一条坏消息把日志刷满。

接口（和页面对应，方便脚本化）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/reply-rules` | 列出全部自动回复规则 |
| POST | `/api/reply-rules` | 新建（`entries` 里放多条回复） |
| PUT | `/api/reply-rules/{id}` | 修改（会顺手清掉这条规则所有回复的记录） |
| DELETE | `/api/reply-rules/{id}` | 删除（连同回复记录） |
| POST | `/api/reply-rules/{id}/toggle?enabled=false` | 启用 / 停用（不改其它字段） |
| POST | `/api/reply-rules/{id}/reset` | 只清回复记录，让「会话只回一次」重新生效 |
| POST | `/api/reply-rules/{id}/merge` | 把同商品、同类型的其它规则并进来（回复记录保留） |

## 自动评价怎么配

买家确认收货后，闲鱼会在私信里推一张系统卡片「快给ta一个评价吧～」。
后台「**设置 → 自动评价**」打开开关并保存，之后收到这种卡片就会自动给买家**好评**。

- **默认关闭**：评价是公开且不可撤销的，是否给每个买家好评应该由运营自己决定。
  环境变量 `XY_AUTO_RATE=0` / `1` 可作为默认值，后台保存过以后以数据库为准。
- **评价文案**：在设置页填写，支持 `{buyer}` `{item_id}` `{order_id}` `{date}`；
  最多 200 字，留空使用默认文案。只会调用 `rate=1`（好评），不会自动给中差评。
- **触发方式**：优先走 IM 推送的评价请求卡片；如果推送漏了，按
  `XY_AUTO_RATE_POLL_INTERVAL`（默认 600 秒）扫最近成交订单兜底，每轮最多评 3 单。
- **不重复**：成功评价过的订单会写进 `rate_records`，之后再推同样的卡片也不会重复调用；
  失败的记录在 1 小时内不会重试，避免把接口刷爆。
- **前提**：订单要已经是「交易成功（买家确认收货）」状态；没确认收货时闲鱼不会允许评价。
  开启 `XY_DRY_RUN=1` 时只打日志、不会真的提交评价。

设置页下方会显示最近 50 条评价记录（订单号、买家、文案、结果、失败原因），也可以直接读接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/rate-records?limit=` | 最近自动评价记录 |
| GET | `/api/config/settings` | 读取自动评价开关 / 文案 |
| PUT | `/api/config/settings` | 保存（`auto_rate_enabled` / `auto_rate_feedback`；不传的字段不改） |

> 评价接口是 `mtop.taobao.idle.rate.create`（v4.0），与网页端一致。
> 如果平台返回风控、已评价、订单状态不允许等原因，会记在评价记录的「详情」列里。

## 在后台直接聊（回复私信）

后台左侧「**聊天**」页就是一个极简版闲鱼私信客户端，专门用来接住那些自动回复没覆盖的问题。

- **左边**：所有会话，按最后一条消息倒序；显示买家名、账号、商品 / 订单、最后一句和**未读红点**。
  多个账号时可以按账号筛选。点一个会话，右边就是完整对话。
- **右边**：收到的消息在左、你发出的在右；底部输入框直接回复。
  `Enter` 发送，`Shift+Enter` 换行。页面每 5 秒自动刷新一次（只读本地库，不额外打闲鱼接口）。
- **新消息提示**：不在聊天页时，买家发来私信会在右下角弹气泡、响一声，
  点气泡直接跳到那个会话；「聊天」左边是全部会话的未读总数。
  新订单另有一套提示（「发货记录」红点 + 三音提示），右上角小铃铛里可以分别关掉。
  提示只在页面开着时生效；关掉页面就收不到，未读数仍然留在库里。
- **打开会话时会补拉历史**：第一次点开某个会话，会通过这条账号的长连接拉一次最近 50 条
  （`/r/MessageManager/listUserMessages`），补进本地流水；失败也不影响看已有的本地记录。
- **发送走同一条长连接**：和自动回复 / 发货消息完全一样的通道（`sendByReceiverScope`），
  发出去的同时记进「消息流水」。手动发送**不受**「同一会话只回一次」和冷却限制 ——
  人点发送就是明确要发。
- **从订单主动开聊**：「发货记录」每行右边有「聊天」。这个买家聊过就复用原会话；
  没聊过就用订单里的商品 ID 建一个（`SingleChatConversation/create`），建好直接进入聊天页。
- **图片 / 视频**：输入框上方有「上传图片 / 上传视频」。图片会先压缩成 JPEG，再上传到闲鱼 CDN；
  视频走网页端 `FileUpload_pre → frag → ci` 分片上传，自动用 ffmpeg 截第一帧当封面。
  发出的视频同时在本机留一份（`XY_MEDIA_DIR/chat`），聊天页通过后台鉴权接口预览。
- **内置图片库**：点「内置图片」打开图库，点一张就发给当前买家；图库里也能上传 / 删除。
  图片存在 `XY_MEDIA_DIR`（默认 `data/media`），不上传第三方图床。
- **撤回**：自己发出、两分钟内的消息，气泡旁边会显示「撤回」。调用闲鱼 IM 的
  `/r/MessageManager/recallMessage`；撤回后气泡变成「你撤回了一条消息」。
  旧版本发出的消息没有服务端 messageId，不显示撤回按钮。
- **前提是账号在线**：账号没连上闲鱼时，历史照样能看，但发送会提示 502 / 409 并写日志。
  先看「账号」页的状态。**发视频的服务器必须安装 `ffmpeg` / `ffprobe`。**

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/chats?account_id=&limit=` | 会话列表（最后一条 + 未读数 + 买家 ID） |
| GET | `/api/chats/{chat_id}/messages?account_id=&sync=` | 会话消息；`sync=true` 先补拉最近历史 |
| POST | `/api/chats/{chat_id}/send` | 发送文本（`account_id` / `text` / 可选 `to_id`、`item_id`、`order_id`） |
| POST | `/api/chats/{chat_id}/send-image` | 发送内置图片（JSON：`account_id` / `image_id` / `to_id`） |
| POST | `/api/chats/{chat_id}/send-image-file` | 上传图片并发送（multipart：`file` + `account_id` 等） |
| POST | `/api/chats/{chat_id}/send-video` | 上传视频并发送（multipart：`file` + `account_id` 等） |
| POST | `/api/chats/{chat_id}/recall` | 撤回（JSON：`account_id` / `message_id`，两分钟内） |
| POST | `/api/chats/{chat_id}/read?account_id=` | 标记已读（清会话未读红点） |
| POST | `/api/chats/open` | 按买家 / 订单打开（必要时创建）会话，返回 `chat_id` |
| GET | `/api/media/images` | 内置图片库列表 |
| POST | `/api/media/images` | 上传内置图片（multipart：`file` / `name`） |
| GET | `/api/media/images/{id}/content` | 读取内置图片（需管理口令） |
| DELETE | `/api/media/images/{id}` | 删除内置图片 |
| GET | `/api/messages?limit=` | 消息流水（最新在前；`system: true` = 系统提示 / 交易事件，不是买家发言） |
| GET | `/api/messages/{id}/media?account_id=&kind=` | 读取本机保存的视频 / 封面（需管理口令） |

几个边界：

- **只同步收到的消息**。本工具发出的消息在发送那一刻就记了流水，不再从历史里补，
  所以不会出现两条一样的气泡；但**你在手机 / 网页闲鱼上亲手发的消息**不会自动进这个页面。
- **聊天历史就是 `messages` 表**，受 `XY_MESSAGE_RETENTION_DAYS`（默认 30 天）约束：
  超过保留期的消息会被清掉，聊天页自然也就看不到了。图片 / 视频消息的本地副本同样会被清理。
- **发送的是文件，不是链接**：图片走闲鱼图片 CDN，视频走 IM 分片上传（`authMediaId`）。
  视频只接受常见格式（推荐 mp4），服务器没装 ffmpeg 时会直接拒绝（503）。
- **大小限制**：图片默认 10 MB、视频默认 20 MB（`XY_MAX_IMAGE_MB` / `XY_MAX_VIDEO_MB`）。
  视频分片上传是几十到几百次 WS 往返，20 MB 已经要几十秒，不建议再往上调。
- **撤回只支持两分钟**：这是闲鱼服务端的限制，本工具在页面和接口两边都会先挡一次。
- 文本单条上限 **2000 字**；发送 60 条/分钟，图片/视频 20 次/分钟，补拉历史 / 打开会话 30 次/分钟，
  超了会返回 429（正常人手点不出来）。

## 消息是怎么收进来的（重要）

闲鱼的私信正文**不保证走 WebSocket 推送**。线上实测：连接正常、心跳也正常时，
`syncPushPackage` 里可能只有

- 会话引导（`contentType` = 8，一次上百条，纯噪声）；
- `{"1": [{"1": "68250276867@goofish", "2": 1, "3": 1, "4": "<我的unb>@goofish"}]}`
  —— **只有会话 ID 和未读标记，没有正文**。

只靠推送的话，日志里就是「收到无法解析的负载」，看起来像没人说话，
实际上买家的话一直都在。所以收消息有两条路：

| 路径 | 触发 | 特点 |
| --- | --- | --- |
| WebSocket 推送 | 实时 | 快，但正文可能缺失 |
| `/r/Conversation/listNewestPagination` | 每 `XY_MESSAGE_POLL_INTERVAL` 秒 | 每个会话的**最后一条**消息（含正文） |
| `/r/MessageManager/listUserMessages` | 上面发现会话有新动静时 | 该会话最近 `XY_MESSAGE_HISTORY_LIMIT` 条，防止连发被漏 |

两条路都走同一个处理入口，靠服务端 `messageId` 去重（`seen_messages` 表），
所以同一条消息不会既被推送回一次、又被拉取回一次。

> 参考 [xianyu-pilot](https://github.com/dameng2026/xianyu-pilot) 的做法：会话列表只给每个会话的
> 最后一条，买家连发两句（「在吗」「发货吗」）时，关键词正好落在被顶掉的那条上，
> 规则就「看起来没生效」。所以发现会话有新动静后再补拉一次该会话的历史，一起处理。
> 补拉是一趟额外的 WS 往返，因此每轮只给最新的 `XY_MESSAGE_HISTORY_CONVERSATIONS` 个会话补
> （默认 5），其余只用最后一条；设成 0 就完全不补。

**启动基线**：第一次拉到的会话里，比「本次连接建立时刻」更早的都算历史消息，
只记已读不回复 —— 否则一重启就会把昨天的消息全部自动回复一遍。
比连接时刻晚的（哪怕只早到几百毫秒）照常处理，不会漏掉启动瞬间到达的那条。

> 代价是自动回复的延迟约等于 `XY_MESSAGE_POLL_INTERVAL`（默认 20 秒）。
> 想更即时可以调到 10，但别低于 5：这是每次都要打一次 WebSocket RPC 的路径。

### 注册流程也有坑（已修）

两个细节会导致「连上了、也收到帧，但永远收不到正文」：

1. **心跳必须在 `/reg` 之前启动**。注册期间长时间没有 `/!`，服务端会把连接判成
   不活跃，之后只推框架帧（`/s/sync`、`/s/vulcan`）不再推消息内容。
   现在 `connect()` 里先发首跳、再注册。
2. **`/reg` 与 ackDiff 之间要留一秒**（`XY_REGISTER_GAP`）。紧凑连发会让注册在
   服务端不生效，症状和上面完全一样。
3. **ackDiff 要周期性重发**（`XY_SYNC_POLL_INTERVAL`，默认 30 秒）。增量推送是服务端
   对 ackDiff 的响应；只发一次的话，除了连接瞬间那批快照包（`/s/sync`、`/s/vulcan`）
   就再没有新消息下来了 —— 这也是「连上了但收不到新消息」的成因之一。

### 排查「为什么没触发」

日志按这个顺序看：

| 日志 | 含义 |
| --- | --- |
| `已建立会话基线（N 个会话）` | 拉取通道通了，N 是当前会话数 |
| `会话 X（买家名）拉到 N 条新消息` | 从拉取通道收到新消息了 |
| `拉取到 X 的消息：…` | 同上，逐条明细（INFO 以下级别） |
| `会话 X 有新消息，但这一帧只有未读标记、没有正文` | 推送通道只给了标记，正文靠轮询补 |
| `这一帧里有 N 条负载解不开（lwp=…）` | 推送格式变了，把整行发我 |
| `已自动回复 X：命中商品自动回复「…」` | 真的发出去了 |
| `不自动回复：命中的规则都在冷却或已回过` | 规则命中了，但被「会话只回一次」或冷却挡住 |

### 额度按站点货币换算（重要）

new-api 的 `quota` 是按**站点展示货币**计价的，由后台 `quota_display_type` 决定：

| 站点货币 | 换算 | 1 元订单得到 |
| --- | --- | --- |
| `USD` | `quota = 金额 × quota_per_unit` | 500000 quota = $1 |
| `CNY`（汇率 7.3） | `quota = 金额 ÷ 7.3 × quota_per_unit` | ≈68493 quota = **¥1** |
| `CUSTOM` | 按 `custom_currency_exchange_rate` | 同 CNY 逻辑 |

程序启动时会读 `/api/status` 拿到 `quota_display_type` / `usd_exchange_rate` 自动换算，
**不需要你手动补偿**。后台「发货规则」页的额度预览也会跟着显示 $ 或 ¥，避免误读。

> 历史坑：早期版本无条件把 `quota_per_unit` 当成「$1 = 500000」。在 CNY 站点上
> 这会让 1 元订单发出 ¥7.30 的额度（多给 7.3 倍）。已修复，且有回归测试锁住。

## 登录态能撑多久（为什么会 1~2 天掉一次）

**结论先说：闲鱼网页登录态有硬 TTL，实测 24 小时整到期，靠请求续不上。**
这不是本项目独有的问题 —— 同类开源项目（比如 XianYuPilo）用的是同一套
`hasLogin` 保活配方，一样会在 1~2 天掉一次；差别只在「掉了以后怎么恢复」。

同一台机器上连续两天的日志：

```
2026-10-27 12:52:52  扫码登录成功（unb=4167468834）
2026-10-28 12:53:21  FAIL_SYS_SESSION_EXPIRED::Session过期
                     ↑ 距登录 24 小时 00 分 29 秒
```

这 24 小时里进程一直在线、订单每 30 秒查一次、`_m_h5_tk` 每 1.5~2.5 小时刷一次，
**几万次带凭据的请求一秒都没能延长它**。三条实测结论：

| 事实 | 实测结论 |
| --- | --- |
| `passport.goofish.com/newlogin/hasLogin.do`（常被当成「保活接口」） | 对**有效 Cookie** 和**垃圾 Cookie**（`unb=12345678; cookie2=garbage`）返回**完全同一行**：`{"titleMsg":"您的登录态已失效，请重新登录","resultCode":100,...,"success":true,"hasError":false}`，而且**永远没有 Set-Cookie**。既判断不了状态，也续不了期 |
| `_m_h5_tk` | `Max-Age=5400`（90 分钟），必须主动刷；但它只是 mtop 的**签名令牌**，和登录票据是两件事 |
| Cookie 有没有 `cookie17` | `cookie17` 是淘宝 passport 的「保持登录」长效票据，下发在 `.taobao.com` 上。**有它**，浏览器才能在 `sgcookie` 过期后静默换新会话；**没有它**，网页登录态就是一天一换 |

所以本项目的策略是「**不假装能续期，改成如实报告 + 提前预警 + 一键重扫**」：

- 保活只保留「顺带合并 Cookie」的作用，**不再用它的返回值判断登录态** ——
  既不会假成功（看着在线其实已经死了），也不会误杀正常账号；
- 真正的健康判定走业务接口 `mtop.idle.web.user.page.nav`（回 `SUCCESS` 才算活着），
  每 30 分钟一次；真过期会立刻停下并提示重扫，而不是等某一单发货时才发现发不出去；
- 单独记「上次**真正登录**的时刻」（刷新 `_m_h5_tk` 不算），到
  `XY_RELOGIN_WARN_HOURS`（默认 20 小时）就在日志里提醒、后台账号卡片标黄
  「登录已 X 小时，接近到期 —— 建议现在重新扫码」；
- 扫码 / 粘贴 Cookie 时，把「有没有 `cookie17`」写进日志和后台，
  一眼看出这个号能不能长期挂机。

**想少扫几次，唯一有效的办法是拿到 `cookie17`**：在浏览器里正常登录闲鱼并
**勾上「保持登录」**，然后 F12 复制整条 Cookie，到后台用「手工粘贴 Cookie」。
判断标准很简单 —— Cookie 里有 `cookie17` 就是长效的。

> 另外两条经验：同一个账号**别在多处反复登录**（多端会互踢，客户端这边表现为掉线）；
> 出口 IP 别乱跳（挂代理 / TUN 全局模式会让服务端直接踢长连接，见「代理 / TUN」）。

## 凭据怎么存的（Cookie 加密落库）

**账号 Cookie 不再明文落盘。** 它是这套系统里最高价值的凭据：拿到它等于拿到闲鱼账号
（能发消息、能点发货、能改价）。现在的存法是：

| 项 | 做法 |
| --- | --- |
| 算法 | AES-256-GCM（每条随机 nonce，附加数据绑定「用途 = 账号 Cookie」，搬到别处解不开） |
| 密文长什么样 | `enc:v1:<base64(nonce‖ciphertext‖tag)>`，带版本号，以后换算法/换密钥可平滑升级 |
| 密钥放哪 | 默认 `data/cookie.key`（0600，目录 0700）。可用 `XY_COOKIE_KEY_FILE` 改 |
| 老数据 | 启动时自动就地加密（一次性、幂等），日志里会写「已把 N 个账号的明文 Cookie 就地加密」 |
| 解不开时 | 后台账号卡片直接显示「Cookie 解密失败：密钥不匹配或数据被改过」，账号不会被当成可用去连闲鱼 |

### 三条必须知道的

1. **密钥丢了 = 所有 Cookie 都读不出来 = 重新扫码。** 这是加密的题中之义：
   能绕过密钥的解密，等于没加密。请把 `data/cookie.key` 单独保管。

2. **备份数据库时不要连密钥一起带走。** 否则「备份泄露」依然等于「账号泄露」。
   推荐两条命令分开跑、分开存：

   ```bash
   # 只备份业务数据（不含密钥）
   sqlite3 data/app.db ".backup /path/to/backup/app-$(date +%F).db"
   # 密钥单独离线保管（1Password / 硬件密钥 / 手抄到纸）
   cat data/cookie.key
   ```

   只有「库 + 密钥」同时泄露才等于账号泄露 —— 比过去任何一份库文件泄露就完蛋要强得多。

3. **别想着回退到旧版本代码。** 旧版本不认识 `enc:v1:` 前缀，会把密文当 Cookie 发出去
   （连不上，后台显示未启动）。要回退就先设 `XY_COOKIE_ENCRYPTION=0` **并**手工把
   `accounts.cookie` 里的密文清空、重新扫码。

> 范围说明：这层只加密 `accounts.cookie`。卡密（`cards`）和买家 Key（`buyer_keys`）
> 仍然明文 —— 它们本来就要发给买家，加密只是把明文从磁盘挪到内存，收益远小于代价。
> 真要连它们一起加密，得先把「导出/对账」的流程改掉，属于另一件事。

### 代理 / TUN（挂梯子后账号掉线）

**所有出站请求一律直连**：闲鱼 HTTP、WebSocket 长连接、扫码登录、new-api / 卡密站，
都不读 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `WS_PROXY` 这些环境变量 ——
即使你在 shell 里 export 过、systemd 里带了、或者从「开着代理的终端」启动，也一样。
启动日志里会写一行「出站连接：一律直连」；环境里确实有代理变量时，还会多打一条
warning 说明它们被忽略了。

原因很直接：**闲鱼看登录 IP**。代理一开、出口 IP 一变，服务端就把长连接踢掉，
后台看起来就是「账号掉线 / 要重新扫码」；代理对 WebSocket 的支持也经常不稳。
这个工具是常驻接单的，不该跟着你临时开的代理走。

**TUN / 透明代理是例外**：FlClash、Clash Verge 的 TUN 模式、Clash 的 TProxy 是在
系统路由层接管流量，程序自己关不掉，只能在代理客户端那边放行：

- 用**规则模式**。全局模式（`mode: global`）会无视 DIRECT 规则，等于把机器人也带进代理。
- 规则片段（Clash Meta / mihomo 语法；进程识别要开 `find-process-mode: always`；路径换成你自己的仓库）：

  ```yaml
  rules:
    - PROCESS-PATH,/home/lumorian/Projects/xianyu-auto-reply/.venv/bin/python,DIRECT
    - DOMAIN-SUFFIX,goofish.com,DIRECT
    - DOMAIN-SUFFIX,dingtalk.com,DIRECT      # 长连接实际连的是 wss-goofish.dingtalk.com
    - DOMAIN-SUFFIX,taobao.com,DIRECT
    - DOMAIN-SUFFIX,alicdn.com,DIRECT        # 图片 / 视频 CDN
    - DOMAIN-SUFFIX,alicdn.net,DIRECT
  ```

- 代理如果接管了 DNS（fake-ip），这些域名还得拿到真实 IP，否则会解析成 `198.18.x.x`，
  程序直连这种地址是连不上的：

  ```yaml
  dns:
    fake-ip-filter:
      - "+.goofish.com"
      - "+.dingtalk.com"
      - "+.taobao.com"
      - "+.alicdn.com"
  ```

- 改完自查一下走的是哪条路：

  ```bash
  ip route get $(getent ahostsv4 wss-goofish.dingtalk.com | awk 'NR==1{print $1}')
  ```

  应该走物理网卡（`eno1` / `wlan0` 这类）；显示 `tun0` / `FlClash` 就说明还在隧道里。

> 为什么不自动处理 TUN：规则在代理客户端里，程序只能决定自己「读不读代理变量」。
> 网络层被接管之后，唯一可靠的办法就是在那一边放行这个进程 / 这些域名。

### 管理后台的安全边界

| 层 | 作用 | 说明 |
| --- | --- | --- |
| `XY_ADMIN_TOKEN` | 口令（恒定时间比较） | 错误 10 次/分钟 → 429；没配时只放行本机 |
| 来源检查 | 没有口令时的兜底 | 只认 `127.0.0.1` / `::1` / `127.*`。**同机反代会把远程请求也变成 127.0.0.1**，所以「挂反代 + 没配口令」等于后台无口令开放；这种部署必须配 `XY_ADMIN_TOKEN` |
| Host 校验 | 挡 DNS rebinding | 恶意域名解析到 127.0.0.1 时 Host 对不上 → 400；域名访问请配 `XY_ALLOWED_HOSTS` |
| 跨站校验 | 挡 CSRF | 写请求要求同源（看 `Origin` / `Sec-Fetch-Site`），curl 之类不受影响 |
| 响应头 | 降低注入与缓存泄漏 | `X-Frame-Options: DENY`、`Content-Security-Policy`、`/api` 一律 `no-store` |
| 代理头 | 不让客户端伪造来源 | uvicorn 固定 `proxy_headers=False`，`X-Forwarded-For` 一律不采信 |

> 没配口令 + `XY_ADMIN_ALLOW_REMOTE=1` **不再**等于「对所有人开放」：这一条现在会被忽略，
> 远程请求一律 401。要远程用就配口令 —— 只放宽来源、不放宽口令，才是安全的那一半。

## 已知边界

- **发货必须可核实**：只有「系统交易卡片形态（`contentType=26` / `dxCard` 键）
  **且**订单号来自服务端结构化字段（卡片 JSON、`reminderUrl` 参数）」才免核实直接信任；
  其余一律去闲鱼查一次订单，确认「状态是待发货 + 买家对得上」才发。
  所以买家自己打「我已付款，等待你发货」不会触发发货，只会在日志和 `orders` 里
  留一条 `blocked` 记录。没有订单号的消息一律不发（没法去重也没法核归属）。
  附注：判断「是不是卡片」只看**键名**，绝不扫字符串值 —— 正文就存在 payload 里，
  买家在聊天框里打一句带 `order_detail?id=…` 的话，以前会被误判成交易卡片并跳过核实。
- 发货消息仍然只发**文本**；图片 / 视频目前只在后台「聊天」页手动发送，发货规则里还不能配图片。
- **视频发送依赖宿主机的 ffmpeg**：视频上传走闲鱼网页端的 `FileUpload_pre → frag → ci` 分片流程，
  单文件上限默认 20 MB；格式支持 mp4 / mov / mkv / webm 等 ffmpeg 能读的格式，推荐 mp4。
  发出的视频会在 `XY_MEDIA_DIR/chat` 留本地副本供后台预览，注意磁盘占用。
- **自动评价需要买家先确认收货**：只有闲鱼推出「快给ta一个评价吧」卡片（或订单列表
  出现「交易成功 + 卖家未评价」）才可能触发；没确认收货的订单不会也不能评价。
  只支持好评（rate=1）；评价发出后不能撤回或修改，开启前请想清楚。
- **自动回复的实时性受轮询间隔限制**：正文主要靠拉会话列表拿到，默认 20 秒一轮。
  推送里如果能解析出正文，当条就会立即回复；拿不到就等下一轮。
- **每条自动回复只回一条**：同一会话里买家连发 3 句，会分别判断，命中的规则若勾了
  「同一会话只回一次」则只回第一条；想每句都回就取消勾选并设好冷却。
- **买家昵称**：付款卡片本身不带昵称（它的 `reminderTitle` 是「等待你发货」这类标题），
  新买家又可能一句话没说过。所以名字按「会话资料 → 聊天记录 → 订单详情」的顺序找，
  全都没有才退回「买家」；一旦拿到真名，同一个人历史上记成「买家」的订单/消息会一并回填。
  只有付款触发语在名字还没落定时才会为此多查一次订单，其它情况复用已在缓存里的订单详情。
- 上游模式依赖闲鱼「卖家订单列表」接口拿金额；接口字段变了会退回 `upstream_failed` 并在 `detail` 里写明原因，不会瞎发。
- **充值模式只能充本站 new-api 的令牌**：买家的 Key 必须是 `XY_NEWAPI_BASE_URL` 那台站点上的，
  别的站点的 Key 无法充值。已有 Key 的模型限制、分组、过期时间都不会被改动；
  令牌已禁用 / 已过期时不会硬充，会记 `topup_failed` 提醒先处理。
- **充值结果未知不自动重试**：请求已经发出但回包丢了（超时 / 502）时，new-api 可能已经加过额度，
  程序会记 `topup_unknown` 并停手，需要到 new-api 后台核对余额后人工处理 —— 宁可少发一单，
  也不重复送额度。
- **`order_id` 策略只认本工具记录过的订单**：买家提供的旧订单号必须在 `orders` 里能查到、
  且是「本人 + `delivered`」。如果这单不是本工具发的（或数据库重装过），没法核对归属，
  会提示「没有找到」。这种情况去后台手工绑定 Key，或把规则切成 `auto`。
- **首次购买请用 `auto` 策略**：`order_id` 策略需要买家手里已经有旧订单号；没有旧单的新买家
  会被提示「没有找到 Key」。可以给首单单独建一个 `auto` 规则 / 商品。
- 买家绑定是**按闲鱼用户 ID** 记的（跨本工具的所有账号生效）。同一个买家换了闲鱼号就是另一个绑定了。
- 订单轮询路径需要先 `create_chat` 建会话才能发消息。回包必须由收帧主循环分发（`dispatch`），
  **不能在业务代码里再开一个 `recv`** —— websockets 会报 `cannot call recv while another coroutine is already running recv`。
- 闲鱼的消息推送格式有三代：**嵌套数字键**（`"1"` → `"6"` → `"3"`，真正的聊天消息）、
  **flat**（`chatType` + `operation`，会话引导/部分通知）、**老提醒格式**（`"1"` → `"10"`）。三种都支持。
  遇到第四种时日志会打出「收到无法解析为买家消息的负载（形状 …）」并附上完整内容，把那段发我就行。
- 消息协议是逆向的网页端行为，闲鱼改版时可能需要跟进（`app/codec.py` 的解析、`app/client.py` 的帧格式最可能受影响）。
- Cookie 有效期通常几天到几周，过期后账号状态会变成 `cookie_expired`，重新粘贴即可。
- **掉登录/风控**：如果日志里出现 `FAIL_SYS_USER_VALIDATE`、`RGV587_ERROR`、`被挤爆啦`，
  那是闲鱼的滑块/风控，不是 Cookie 失效。程序会标成 `risk_control` 并长退避重试，
  不会再把 worker 停掉；此时重新扫码也会自动重启该账号的 worker。
  真正过期只会是 `FAIL_SYS_SESSION_EXPIRED` / `请登录`，状态才是 `cookie_expired`。
